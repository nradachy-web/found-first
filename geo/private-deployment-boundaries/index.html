GEO for software sold with a private deployment option

If your SaaS product offers private deployment, use GEO to spell out which components the customer actually operates. A comparison becomes useful to an enterprise architect when it shows what still depends on the vendor during ordinary use.

Follow one workload across the architecture

Use the deployment diagram and installation guide to trace a submitted job through scheduling, execution and result retrieval. Name the operator of each component and the information that crosses the customer's boundary. A diagram with a worker inside a private network can establish where code runs while leaving the scheduler's location unresolved.

Describe the buyer's operating condition

Some buyers can allow a continuing outbound connection. Others must complete jobs while disconnected. Have the agency check installation, licensing, updates and routine execution as separate dependencies before using language such as 'offline deployment.' A documented ability to finish a running job supports a narrower claim than starting new jobs while disconnected.

A build runner behind the customer's firewall

Consider a hypothetical build service with a customer-installed runner. The installation guide points the runner at a vendor-operated scheduler, and the job diagram shows source files processed on the customer's machine. Market that configuration to teams seeking local execution that can reach the scheduler. If procurement requires a disconnected facility to submit fresh builds, the standard configuration leaves a gap. A documented local scheduler and a disconnected installation procedure would justify describing a separate deployment option and the operational duties it gives the customer.
